PROJECT OVERVIEW
----------------
Invoice Extractor is a web-based application that automatically reads invoice
images or PDFs and extracts all important data using AI. Instead of manually
typing invoice details, you upload a file and the system returns structured
JSON data within seconds.

The system is built specifically for real-world Indian pharmaceutical and
hospital invoices (primarily LMMF Deenanath Mangeshkar Hospital supply chain).
These invoices are complex — multi-page, multi-vendor, duplicate/triplicate
copies, free items, GST breakdowns, multiple discount types, mixed GST slabs,
items split across pages, and PO numbers hidden in remarks sections.

--------------------------------------------------------------------------------
TECH STACK
--------------------------------------------------------------------------------

  Backend   : Python 3.11, Flask (web server on port 8001)
  Frontend  : HTML + CSS + JavaScript (single-file UI, no frameworks)
  Primary AI: qwen/qwen3.7-plus  (items pass — character-level accuracy)
  Fast AI   : qwen/qwen3.7-flash (header/totals/verify — speed + cost)
  API Route : OpenRouter (https://openrouter.ai)
  PDF       : PyMuPDF (renders PDF pages to images)
  Image     : OpenCV + Pillow (rotation, contrast, compression)
  Tracing   : LangSmith (full request/response traces for debugging)
  Cache     : File-based SHA-256 hash cache (JSON files in uploads/.cache/)

--------------------------------------------------------------------------------
TWO-MODEL STRATEGY (CURRENT)
--------------------------------------------------------------------------------

The system uses TWO different models for different passes:

  PASS 1 (Header fields) → qwen/qwen3.7-flash (FAST model)
    Fast, cheap. Header fields like invoice number, dates, names, GSTINs
    are large readable text. No need for character-level accuracy.

  PASS 2 (Financial totals) → qwen/qwen3.7-flash (FAST model)
    Fast, cheap. Total amounts, GST sums, round-off values are clear numbers.

  PASS 3 (Line items) → qwen/qwen3.7-plus (PRIMARY model)
    Expensive, accurate. Batch codes like "RUA12505A" vs "RUA12505B",
    item codes like "SR-06-1905" vs "SR-06-1905", expiry dates — all
    require character-level precision. Flash would misread these.

  VERIFICATION → qwen/qwen3.7-plus (PRIMARY model)
    Cross-checks extracted JSON against the invoice image.
    Flags critical mismatches in amounts, quantities, batch codes.

WHY THIS MATTERS:
  - Flash is ~13x cheaper than Plus
  - Passes 1 and 2 use Flash = low cost, fast response
  - Pass 3 (most important) uses Plus = max accuracy where it counts
  - Net result: good balance of cost, speed, and accuracy

ENV CONFIGURATION:
  MODEL_NAME=qwen/qwen3.7-plus         ← primary model (items)
  FAST_MODEL_NAME=qwen/qwen3.7-flash   ← fast model (header/totals)
  FAST_MODEL_API_KEY=                  ← optional separate key for flash

--------------------------------------------------------------------------------
SYSTEM ARCHITECTURE — HOW DATA FLOWS
--------------------------------------------------------------------------------

  1. User uploads invoice (PDF / JPG / PNG / TIFF / BMP / WebP)
         |
  2. app_web.py receives file → checks cache
     --> If cached: return instantly (skip all steps below)
     --> If new: continue
         |
  3. pdf_utils.py converts PDF pages to images (if PDF)
         |
  4. preprocessing.py cleans each image:
         |-- Detects rotation (heuristic-based)
         |-- Applies CLAHE contrast enhancement
         |-- Compresses image for API payload limits
         |
  5. Copy detection (model_client.py)
         |-- Classifies invoice as ORIGINAL / DUPLICATE / TRIPLICATE
         |-- Only UNIQUE pages are sent for extraction
         |-- Duplicate/triplicate pages are skipped
         |
  6. Multi-pass extraction (model_client.py)
         |-- Pass 1: Header fields    → Flash model
         |-- Pass 2: Financial totals → Flash model
         |-- Pass 3: Items per page   → Plus model
         |   |-- Continuation hints injected for items split across pages
         |   |-- Chunked extraction fallback if model hits output limit
         |
  7. Continuation merge (model_client.py)
         |-- Items split at page boundaries are stitched together
         |-- Orphan continuation rows merged into preceding item
         |
  8. Deduplication (model_client.py)
         |-- Removes identical items appearing across duplicate pages
         |
  9. app_web.py post-processing
         |-- OCR corrections (ocr_corrector.py)
         |-- invoice_amount round-off reconciliation
         |-- Type normalization (strings → numbers, date formatting)
         |-- GSTIN validation and hardcode overrides (gstin_validator.py)
         |-- Seller GSTIN lookup (seller_gstin_lookup.py)
         |
 10. GST enrichment (gst_enrichment.py)
         |-- Fills missing per-item GST fields
         |-- Validates GST component consistency
         |-- GST_AMT = CGST + SGST (component-sum method, not bulk calc)
         |
 11. Free item splitting (free_item_splitter.py)
         |-- Splits "20+2" quantities into 2 separate records
         |
 12. Consistency check (consistency_checker.py)
         |-- Cross-validates all financial figures
         |-- Flags discrepancies as _needs_review
         |
 13. Verification pass (model_client.py)
         |-- Sends extracted JSON + image back to Plus model
         |-- Detects critical mismatches (wrong items, missing items, etc.)
         |
 14. Cache result + return JSON to browser
         |
 15. templates/index.html displays result in 5 tabs

--------------------------------------------------------------------------------
FILE-BY-FILE EXPLANATION
--------------------------------------------------------------------------------

1. app_web.py
   -----------
   Role: Main Flask server — orchestrates the entire pipeline
   Port: 8001 (changed from 5000)

   Key responsibilities:
   - Receives uploaded files and runs the full extraction pipeline
   - Applies OCR corrections via ocr_corrector.py
   - invoice_amount round-off reconciliation:
       If extracted invoice_amount + round_off gives a rounder number,
       the system corrects invoice_amount to the TO PAY value.
       Example: 69221.18 + (-0.18) = 69221.00 → fixes to 69221.00
   - Type normalization: "3,053.68" → 3053.68, dates → DD/MM/YYYY
   - Calculates total_quantity as sum of PAID items only (free_item_yn="0")
   - Serves /api/extract (POST) and /api/health (GET)

   LangSmith tracing is enabled — every extraction is logged with full
   input/output for debugging via LANGCHAIN_API_KEY in .env


2. schema.py
   ----------
   Role: AI prompt definitions — the rulebook for the AI

   Contains carefully written rules for every field. Key sections:

   MULTI-LINE PRODUCT CELL RULE (recently added):
     Some invoices print Batch/Expiry/Code below the product name in
     the same table cell. Example:
       Line 1: SP 8747 H 1 (Centilene : 7-0 9.3mm...)
       Line 2: Batch : CF 289
       Line 3: Expiry : 30-Jun-30
       Line 4: Code : AL-02-1234
     Rule: description = Line 1 only. Other lines → their own fields.

   INVOICE_AMOUNT PRIORITY (recently added):
     Some invoices show "Total Amount" AND "TO PAY" separately:
       Total Amount = 69221.18  (pre round-off)
       Round Off    = -0.18
       TO PAY       = 69221.00  ← this is invoice_amount
     Priority: TO PAY > NET PAYABLE > GRAND TOTAL > Invoice Amount

   MIXED GST SLAB HANDLING (recently added):
     If invoice has items at 5% AND 18% GST:
       total_gst_rate = null  (no single rate exists)
       total_cgst_rate = null
       total_cgst_amount = SUM of all CGST rows from GST summary table
     Single-slab invoices: total_gst_rate = CGST% + SGST% as before.

   MULTI-ROW GST SUMMARY TABLE (recently added):
     Some invoices have GST breakdown by rate:
       5%  → CGST: 1198.47,  SGST: 1198.47
       18% → CGST:  311.57,  SGST:  311.57
       Total CGST: 1510.04   Total SGST: 1510.04
     Rule: extract from TOTAL row, not first/individual rows.

   3 focused prompts (pass separation):
     get_header_prompt()  → header fields only
     get_totals_prompt()  → financial totals only
     get_items_prompt()   → line items only


3. model_client.py
   ----------------
   Role: All AI model communication, extraction orchestration

   Key additions since original version:

   TWO-MODEL ROUTING:
     call_fast() → uses FAST_MODEL (Flash) for header/totals/verify
     call_primary() → uses PRIMARY_MODEL (Plus) for items pass
     Separate API keys supported (FAST_MODEL_API_KEY env var)

   COPY DETECTION:
     classify_copy() detects ORIGINAL / DUPLICATE / TRIPLICATE / HOSPITAL
     Multi-page PDFs often have 2-3 identical pages (customer/transporter/
     office copies). Only UNIQUE content pages are extracted.

   CHUNKED EXTRACTION (recently added):
     Problem: Some invoices have 10-15 items. Qwen3.7-plus stops mid-JSON
     after ~3000 chars, truncating to 4 items.
     Solution: If extracted items < 8, automatic chunked fallback:
       - Split invoice image into top 55% and bottom 55% (10% overlap)
       - Extract each chunk separately (5-6 items fits within limit)
       - Merge results with deduplication at chunk boundary
       - Continuation hint passed to bottom chunk for split items
     Cost: 2 API calls only when needed (large invoices)
     Normal invoices (≤7 items): 1 API call as before.

   _extract_items_chunked():
     Handles item continuations within chunks:
       - If top chunk's last item is missing Batch/Expiry, passes hint
       - Bottom chunk receives: "Previous item 'X' may be incomplete"
       - Bottom chunk returns _continuation_for_previous_page=true if needed
       - Merge logic patches continuation data into top chunk's last item
     Deduplication at boundary: description+Batch match check
     None safety: all .get() calls use str(val or '') pattern

   CONTINUATION MERGE:
     Items split across page boundaries are detected and merged:
       Page 1 item: description + qty, but Batch=null (data on page 2)
       Page 2 first row: Batch + Expiry, no description
       Merge: patches Batch/Expiry/Code into the prior item
     _is_continuation(): detects rows with metadata but no description
     _CONTINUATION_FIELDS: Batch, expiry_date, item_code, hsn_sac, Pack, MRP

   max_tokens per pass:
     Header:       4,000 tokens
     Totals:       6,000 tokens
     Items (multi-page): 16,000 tokens (increased from 8,000)
     Items (single-page): 16,000 tokens
     Chunked items:       8,000 per chunk


4. ocr_corrector.py
   -----------------
   Role: Deterministic post-extraction fixes (no API calls)

   Key rules applied after AI extraction:

   DESCRIPTION FIELD PARSING (recently added):
     Detects if Batch/Expiry/Code/MRP keywords appear inside description.
     Example (wrong): "SP 8747 H 1 (Centilene...) Batch : CF 289 Expiry : 30-Jun-30"
     Fix:
       description = "SP 8747 H 1 (Centilene...)"  (cleaned)
       Batch = "CF 289"  (extracted from description)
       expiry_date = "30/06/2030"  (extracted from description)
     Rule: Only fills fields that are currently empty. Never overwrites.

   BATCH CORRECTIONS:
     Human-verified batch lookup table (batch_corrections.json)
     Maps known misread batch codes to correct values.

   GSTIN CORRECTIONS:
     Single-character OCR fixes (1→I, 0→O for known positions)
     Hardcode overrides for known customer GSTINs
     (Deenanath hospital GSTIN is hardcoded to prevent misread)

   DATE NORMALIZATION:
     All expiry date formats → DD/MM/YYYY
     Handles: MM/YY, MM-YY, MM/YYYY, DD-MMM-YY, DD-Mon-YYYY


5. gstin_validator.py
   -------------------
   Role: GSTIN format validation and correction

   GSTIN format: 2-digit state code + 10-digit PAN + 1Z + 1 check digit
   Validates structure, corrects common OCR errors (O↔0, I↔1, S↔5)
   Hardcoded overrides for known customers that AI consistently misreads.


6. seller_gstin_lookup.py
   -----------------------
   Role: Seller GSTIN hardcode lookup table

   Maintains a lookup of seller names → correct GSTINs.
   When seller GSTIN is extracted with low confidence, this overrides it.
   Prevents systematic misreads for repeat vendors.


7. consistency_checker.py
   -----------------------
   Role: Cross-validates extracted financial figures

   Checks:
   - Rate × Qty ≈ AMOUNT (within tolerance)
   - AMOUNT - Discount ≈ taxable_value
   - taxable_value × GST% ≈ GST_AMT (within 5 paisa)
   - CGST + SGST ≈ GST_AMT
   - Sum of item GST_AMTs ≈ total_gst_amount
   - invoice_amount ≈ sum of line totals + round_off

   Flags items with _needs_review=true and _review_reasons=[...]
   Non-blocking: extraction succeeds even if checks fail.


8. gst_enrichment.py
   ------------------
   Role: Per-item GST derivation and validation

   GST_AMT COMPONENT-SUM FIX (recently added):
     Old behaviour: GST_AMT = round(taxable × rate%)
     Problem: taxable=3987.78, rate=5%
       Direct:     round(3987.78 × 5%) = 199.39
       Components: CGST=99.69, SGST=99.69 → sum=199.38
       Mismatch: 199.39 ≠ 199.38 (matches invoice line-by-line)
     Fix: Calculate components first, then GST_AMT = CGST + SGST
     This matches how invoice printers calculate line-by-line rounding.

   enrich_item_gst() priority:
     1. Printed components (CGST + SGST) → keep, source="invoice"
     2. GST_AMT and Gst% → split into components
     3. taxable_value and Gst% → calculate all
     4. Nothing available → source="not_calculated", leave null

   taxable_value correction:
     If taxable_value × GST% ≠ GST_AMT (by >5 paisa), and
     Value - Discount × Value matches better → corrects taxable_value
     This catches the common error of model copying gross Value into
     taxable_value field (ignoring discount).


9. free_item_splitter.py
   ----------------------
   Role: Splits free/bonus items into separate records

   Handles quantity formats: "20+2", "20 + 2", separate free_qty column
   Paid record: qty=20, free_item_yn="0", original prices
   Free record:  qty=2,  free_item_yn="1", proportional prices
   total_quantity = sum of paid quantities only


10. pdf_utils.py
    -------------
    Role: PDF to image conversion using PyMuPDF (fitz)
    DPI: 150 (configurable via RENDER_DPI in .env)
    Returns list of PIL Images (one per page)
    Page count limited by MAX_PDF_PAGES (default: 10)


11. preprocessing.py
    -----------------
    Role: Image cleaning before AI extraction

    Pipeline per image:
    1. Rotation correction (heuristic: ink density at top vs bottom)
    2. CLAHE contrast enhancement (improves faded text)
    3. Compression for API limits:
       - Tries JPEG 95%, 90%, 85%, 80% in sequence
       - Tries resolution scaling if size still too large
       - NEVER fails — always sends best available quality


12. cache_manager.py
    -----------------
    Role: Caches results to avoid reprocessing same invoices
    Key: SHA-256 hash of (file bytes + extraction options)
    Storage: uploads/.cache/{hash}.json
    TTL: 24 hours (CACHE_MAX_AGE_HOURS in .env)
    Instant cache hit shown as "⚡ Cached Result" in UI


13. fetch_traces.py / fetch_traces2.py / trace_latest.py
    -------------------------------------------------------
    Role: LangSmith trace inspection tools

    Used for debugging extraction failures:
    fetch_traces.py   → fetches recent traces from LangSmith project
    fetch_traces2.py  → alternative trace fetcher with filtering
    trace_latest.py   → shows the most recent trace in detail

    Traces include: full prompts sent, full AI responses received,
    timing per pass, token usage, errors.


14. batch_corrections.json
    -----------------------
    Role: Human-verified batch number correction lookup

    Format: {"WRONG_BATCH": "CORRECT_BATCH", ...}
    When AI extracts a known misread batch, this corrects it.
    Built up over time from real invoice errors found in production.


15. ocr_client.py
    -------------
    Role: (Legacy) Baidu Qianfan OCR for rotation detection
    Currently: rotation detection uses heuristic method in preprocessing.py
    This file is kept for reference but not in main pipeline.


16. gst_calculator.py
    ------------------
    Role: GST validation following Indian GST rules
    Intra-state: CGST = SGST (equal split)
    Inter-state: IGST only
    Fills missing total GST fields from item-level data.


17. templates/index.html

    Tab 4: JSON        — Syntax-highlighted raw JSON + download + copy

--------------------------------------------------------------------------------
KEY FEATURES — DETAILED EXPLANATION
--------------------------------------------------------------------------------

FEATURE 1: 3-PASS EXTRACTION + TWO-MODEL STRATEGY
---------------------------------------------------
Pass 1 → Flash (header)  : invoice_number, invoice_date, customer, seller, PO
Pass 2 → Flash (totals)  : invoice_amount, round_off, total_gst, cgst, sgst
Pass 3 → Plus  (items)   : All line items — description, batch, qty, price, GST
Verify → Plus  (check)   : Cross-validate extracted data vs invoice image

Why separate passes?
- Each pass is focused → better accuracy than one giant prompt
- Flash for easy fields = cost saving (13x cheaper)
- Plus for critical batch codes = accuracy where it matters
- If one pass fails, others still succeed


FEATURE 2: COPY DETECTION + DEDUPLICATION
------------------------------------------
Problem: A 4-page PDF is often: Original + Duplicate + Triplicate + Hospital Copy
         All 4 pages have the same items. Without dedup, you get 40 items instead of 10.

Solution:
- classify_copy() sends each page to model: "What copy type is this?"
- Returns: ORIGINAL / DUPLICATE / TRIPLICATE / HOSPITAL
- Only UNIQUE pages (typically 1-2) are sent for item extraction
- After extraction: signature-based dedup removes remaining duplicates
  Signature: (description + batch + quantity + unit_price)


FEATURE 3: CHUNKED EXTRACTION (AUTOMATIC FALLBACK)
---------------------------------------------------
Problem: Qwen3.7-plus stops generating JSON after ~3000 chars.
         11-item invoice → only 4 items extracted, 7 missing.

Solution (automatic, triggered only when needed):
- Normal extraction runs first (1 API call)
- If result has < 8 items → chunked fallback triggers automatically
- Image split: top 55% + bottom 55% (10% overlap for safety)
- Each chunk extracted separately (5-6 items each, fits in 3000 chars)
- Chunk boundary: continuation hint passed for split items
- Results merged with dedup at boundary
- Cost: +1 API call only for large invoices

Normal invoices (≤7 items): unaffected, no extra cost


FEATURE 4: ITEM CONTINUATION ACROSS PAGE BOUNDARIES
----------------------------------------------------
Problem: Item on page 1 shows description + price. Batch/Expiry printed on
         page 2 (item row continues to next page).

Solution (multi-level):
Level 1 — Continuation hint to model:
  Before extracting page N, tell model:
  "Previous page ended with item 'X' (Batch=null, Expiry=null).
   If top of this page shows Batch/Expiry for that item,
   return it as {_continuation_for_previous_page: true, Batch: ..., Expiry: ...}"

Level 2 — Continuation merge in code:
  _is_continuation() detects rows with metadata but no description
  Merge logic patches fields into the preceding item
  Fields that can continue: Batch, expiry_date, item_code, hsn_sac, Pack, MRP

Level 3 — Forward-look orphan patch:
  Safety net for items where model returned continuation as a full item
  Matches by: prior item missing Batch+Expiry+Code AND next item has them

Level 4 — Chunked extraction continuation:
  Same logic applied within a single page when chunks are used


FEATURE 5: DESCRIPTION FIELD CLEANING
--------------------------------------
Problem: Some invoices print Batch/Expiry/Code below product name in same cell:
  "SP 8747 H 1 (Centilene...) Batch : CF 289 Expiry : 30-Jun-30 OLD MRP : 31584"
  Model dumps everything into description field.

Solution (two layers):
Layer 1 — Prompt rule (schema.py):
  Explicit multi-line product cell rule:
  description = first line only (product name)
  Remaining lines → extract to Batch, expiry_date, item_code, MRP fields

Layer 2 — Post-processing parser (ocr_corrector.py):
  If description contains "Batch:", "Expiry:", "Code:", "MRP:" keywords:
  - Regex extracts each field
  - Fills target field ONLY if currently empty (never overwrites)
  - Strips sub-lines from description
  - Handles: "Batch : CF 289", "Expiry : 30-Jun-30", "Code : AL-02-1234"


FEATURE 6: GST_AMT COMPONENT-SUM ROUNDING FIX
-----------------------------------------------
Problem: Bulk calculation gives different result than component sum:
  taxable = 3987.78, GST = 5%
  Bulk: round(3987.78 × 5%) = 199.39
  CGST: round(3987.78 × 2.5%) = 99.69
  SGST: round(3987.78 × 2.5%) = 99.69
  Component sum: 99.69 + 99.69 = 199.38 ← matches actual invoice

Fix: Calculate CGST and SGST first, then GST_AMT = CGST + SGST
     Not: calculate GST_AMT first, then derive components.
     This matches how invoice systems calculate line-by-line.


FEATURE 7: INVOICE_AMOUNT RECONCILIATION
-----------------------------------------
Problem: Some invoices show both "Total Amount" and "TO PAY":
  Total Amount = 69221.18  (pre round-off subtotal)
  Round Off    = -0.18
  TO PAY       = 69221.00  ← this is what customer pays

Model sometimes extracts Total Amount instead of TO PAY.

Solution (two layers):
Layer 1 — Prompt priority rule:
  TO PAY > NET PAYABLE > GRAND TOTAL > Invoice Amount

Layer 2 — Post-processing reconciliation (app_web.py):
  If extracted invoice_amount + round_off = rounder number (ends in .00/.50):
  Automatically corrects invoice_amount to the rounded value.
  Safe: only triggers when round_off exists and difference > 1 paisa.


FEATURE 8: MIXED GST SLAB HANDLING
------------------------------------
Problem: Invoice with items at 5% and 18% GST.
  Old behaviour: total_gst_rate = 5 (picked first/only slab)
  Wrong: there is no single total rate.

Fix:
  If GST summary table has multiple non-zero rate rows:
    total_gst_rate = null
    total_cgst_rate = null
    total_cgst_amount = SUM of all CGST rows (from Total row of GST table)
    total_sgst_amount = SUM of all SGST rows (from Total row of GST table)
  Single-slab invoices: unchanged behaviour.


FEATURE 9: LANGSMITH TRACING
------------------------------
Every extraction creates a trace in LangSmith project "invoice-extractor".
Each trace shows:
- All 3-4 API calls with full prompts and responses
- Token usage per pass
- Timing per pass
- OCR corrections applied
- GST enrichment decisions
- Consistency check results

Use fetch_traces.py or trace_latest.py to inspect failures.
LANGCHAIN_API_KEY set in .env.


FEATURE 10: SMART CACHING
---------------------------
SHA-256 hash: file bytes + extraction options
Same invoice + same settings → instant cache hit (no API calls)
Cache stored in uploads/.cache/{hash}.json
TTL: 24 hours (configurable)
Shown in UI as "⚡ Cached Result" badge


--------------------------------------------------------------------------------
FINANCIAL FIELD SEMANTICS (AUTHORITATIVE DEFINITIONS)
--------------------------------------------------------------------------------

  Value           : Gross line amount BEFORE discount (qty × rate)
  taxable_value   : Net taxable amount AFTER discount, BEFORE GST
  total_price     : Final line total INCLUDING GST
  invoice_amount  : Final amount customer must pay (= TO PAY on invoice)
  GST_AMT         : CGST + SGST + IGST for one line item
  round_off       : Signed rounding adjustment (can be + or -)

  Value ≠ taxable_value (except when invoice has no discount)
  invoice_amount ≠ "Total Amount" (when round_off exists)

  null vs "0.00":
    null   = field not applicable / not present in invoice
    "0.00" = explicitly zero monetary total

Note: invoice_amount, total_*_amount are kept as strings.
      taxable_value, Gst%, cgst_rate, sgst_rate are numbers.
      GST_AMT is a string.

--------------------------------------------------------------------------------
KNOWN ISSUES / FUTURE RISKS
--------------------------------------------------------------------------------

1. MULTIPLE DISCOUNTS IN ONE FIELD
   Some invoices have TD%, CD%, Scheme% as separate columns.
   Current schema has one Discount field.
   Safe mitigation: If TAXABLE column printed, trust it (never reconstruct).

2. EXTRA CHARGES NOT IN SCHEMA
   Freight, Packing, TCS, CN/DN amounts affect final total.
   Current schema extracts invoice_amount as final payable (handles it).
   But individual extra-charge fields not captured.

3. VALUE vs TAXABLE_VALUE CONTRADICTION IN PROMPT
   Schema.py lines 1148 vs 1422 have conflicting rules.
   Line 1148: "Never copy taxable_value into Value"
   Line 1422: "Copy TAXABLE to BOTH Value and taxable_value"
   Documented in PROMPT_CONTRADICTIONS_AUDIT.md.
   Not yet fixed — requires careful regression testing.

4. CHUNKED EXTRACTION FOR > 15 ITEMS
   If an invoice has 20+ items, even chunked (2 chunks) may not be enough.
   Future fix: 3-chunk strategy or dynamic chunk count based on image height.

5. MIXED GST + DISCOUNT
   Invoice with both multiple GST slabs AND multiple discount types
   not yet seen in production. May require special handling.
